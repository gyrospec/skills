# Implement

This skill runs a slug's sub-tickets in **waves**. A wave takes the **frontier** (every ready sub-ticket), writes all their plans in parallel, gets one human review of the whole wave, then implements the tickets in parallel, each in its own worktree. Everything lands on one **integration branch**, which gets one code review and one PR at the end. `/gyro-writing-plans` followed by `/gyro-executing-plans` is the cheaper route, one sub-ticket at a time; this one is faster and spends more. This workflow adapts `implement-spec` from mattpocock/skills; attribution is in this folder's `NOTICE.md`.

You are the controller. Start every subagent with a fresh context window, never a fork of this conversation. Talk to subagents through pointers (slug, ticket number, plan path, branch, commit), not pasted content. Only you run `gyro ticket` and edit `.gyro/`; subagents never do. If the harness cannot run subagents in the background or give each one its own worktree, say so, suggest the one-at-a-time route, and stop.

1. Call the Skill tool with "gyro". Follow its Node 20+ check, script path, language, and format rules. Reply in the user's language and keep convention keywords English.
2. Require `<slug>` and run `gyro status <slug> --json`. Require the approved spec and its upstream gates to be current and not stale, and require that `gyro check <slug> tickets` is clean; otherwise show the lines, suggest the correcting phase (usually `/gyro-breakdown <slug>`), and stop. The frontier is every sub-ticket with `ready: true`. If the frontier is empty and no ledger below records work in flight, show `next` and stop.
3. Settle the run's authority and baseline before touching anything:
   - Explain that this run makes local commits: an integration branch `gyro/<slug>`, one branch per sub-ticket, and merges between them. Ask once for that authority. Without an explicit yes, stop and suggest `/gyro-writing-plans <slug> <nn>`. Pushing and opening the PR belong to `/gyro-ship <slug>` (step 9).
   - Run `git status --porcelain`. Changes in the tree are someone else's WIP: ask the user to commit or set them aside, and never stash or discard them yourself.
   - The **run ledger** is `docs/superpowers/plans/<slug>-implement.md`. If it exists, this is a resume: check out its integration branch, reuse its `**Base:**`, and continue from what it records for each ticket. Otherwise create `gyro/<slug>` from `HEAD`, write the ledger with `**Integration branch:** gyro/<slug>` and `**Base:** <output of git rev-parse HEAD>`, and commit it. Record every plan, branch, merge, status change, and blocker in it as the run goes.
4. **Plan the wave.** For each frontier ticket without a plan at the current spec revision, start a planner subagent in the background, all at once. Brief each one with the repository root, the slug, and the ticket number, and tell it to call the Skill tool with "gyro", read `PLANNING.md` in that skill's directory, write that one plan, edit nothing else, and report the plan path plus any decision it had to report. When every planner has reported:
   - Check each plan's `Ticket`, `Sub-ticket`, and `Spec revision` header and its `## Files` list. Plans in one wave whose files overlap cannot run side by side: keep the lower ticket number in this wave and move the other to the next one.
   - Bring every reported decision to the user. A decision that changes approved scope stops that ticket; suggest the phase that owns it.
   - Show all the wave's plan paths in one message, with a short summary of each and the tickets you moved, and ask the user to review them. Revise what they ask for, yourself or with a fresh planner. Implement only the plans the user explicitly clears; the rest wait.
   - Commit the cleared plans to the integration branch.
5. **Implement the wave.** For each cleared ticket, run `gyro ticket <slug> <nn> --status in_progress`, commit, and start an implementer subagent in the background on its own branch `gyro/<slug>-<nn>` in its own worktree from the integration tip (the harness's worktree isolation where it has one, otherwise `git worktree add`). Brief it with the worktree path, the plan path, the slug, and the ticket number, and tell it to:
   - confirm its worktree is based on the integration tip and reset onto it if not, then add `**Execution start:** <sha>` under its plan's header;
   - call the Skill tool with "gyro", read `EXECUTING.md` in that skill's directory, and follow all of it for this plan;
   - never edit `.gyro/` or run `gyro ticket`, and commit its work on its own branch only;
   - before reporting, merge the integration tip into its branch and rerun the project's test command;
   - report its branch, last commit, the test command's result, any deviation from the plan, or the blocker with its evidence.
6. **Merge reports one at a time, as they arrive.**
   - A blocker: run `gyro ticket <slug> <nn> --status blocked --reason "<why>"`, keep the branch, and tell the user. Do not retry past the cap in `EXECUTING.md`.
   - Finished: check the evidence and merge its branch into the integration branch. If it no longer merges cleanly because another branch landed first, send it back to merge the new tip (continue that implementer, or start a fresh one on its branch); resolve a conflict yourself only when it is mechanical. Run the project's test command on the integration branch. When it is green, run `gyro ticket <slug> <nn> --status done` without `--pr` (here done means verified on the integration branch; the PR link follows in step 9), commit, and remove the worktree. When it is red, send the work back as a failed attempt that counts toward the cap.
   - After every merge, run `gyro status <slug> --json`. Tickets that just became ready form the next wave: plan them by step 4 while the rest of this wave keeps running.
7. When nothing is in flight and the frontier is empty, run `gyro status <slug> --json` again: the PRD, prototype, and spec gates are current (a gate shows `draft` when its file was edited without re-approval), no ticket of this run is stale, and every plan's `Spec revision` equals the current approved revision. If any check fails, mark the affected tickets `blocked` with the failed check as the reason, name the phase that fixes it, and stop. Never edit `gates.json`, snapshots, or `spec_revision` to get past it.
8. Call the Skill tool with "code-review" on the integration branch. Give it the ledger's `**Base:**` as the fixed point, and as the spec source the approved spec snapshot `.gyro/<slug>/approved/spec.<n>.md` with every sub-ticket file and plan of this run. Local mode has no issue tracker, so tell it not to look for one or ask for `/setup-matt-pocock-skills`. Fix every Critical and Important finding with one fresh implementer subagent in a worktree from the integration tip, failing test first, following `EXECUTING.md`; merge it, rerun the tests, and review the corrections until those findings are resolved. Record every finding and how it was settled under `## Review findings` in the ledger.
9. Do not push or open the PR here. When the user already has a real `http://` or `https://` PR URL from `gyro/<slug>`, run `gyro ticket <slug> <nn> --status done --pr <url>` for every ticket this run finished. Otherwise those tickets stay done without a PR link: say so in the report and in the ledger, never invent a URL, and tell the user that `/gyro-ship <slug>` checks, pushes, opens the PR from the integration branch, attaches UI screenshots, and records the URL.
10. Run `gyro status <slug> --json` and `gyro status <slug>`. Report each ticket of this run as done or blocked, with its evidence and branch. Tell the user the next step is `/gyro-ship <slug>` while the run has no PR, and the returned `next` after that, and recommend `/gyro-retro <slug> <nn>` for each ticket that hit a blocker, a deviation, or a review finding. Stop. Never invoke another phase automatically.
